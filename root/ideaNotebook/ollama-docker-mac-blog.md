## 1. はじめに（リード・現象）

セキュリティ訓練用 Web アプリの管理画面で、「AI で訓練メールを自動生成」する機能を用意していた。  
ところが **Mac の Docker 環境で動かしていると、生成ボタンを押してから数分待っても処理が終わらない**。  
一見するとフロントのタイムアウトや API の設定不足のように見えたが、実際にブラウザとログで追いかけた結果、**単なるタイムアウト設定の話ではなく、Docker for Mac の仕様に起因する「GPU が使えないこと」が根本原因**だった。

---

## 2. 調査で分かったこと

- ブラウザ（Browser Subagent）で管理画面から「自動で生成する」を実行し、動作とログを確認。
- **Ollama 側に「約 5 分」のハードタイムアウト**があり、それを超えると水面下でエラー終了していた。
- フロントはその間ずっとレスポンスを待ち続けているため、「終わらない」ように見えていた。
- つまり「アプリのタイムアウト設定が甘い」だけでなく、**そもそも生成が 5 分以内に完了していなかった**。

---

## 3. 根本原因：Docker for Mac では GPU が使えない

### 3.1 仕様の要点

- **Docker for Mac** は、Mac の上で **Linux 用の仮想マシン（VM）** を動かし、その中でコンテナを実行する。
- **Apple Silicon の GPU（Metal）** は、**macOS 用のドライバ・フレームワーク**で提供されている。
- Linux VM からは、その Metal/GPU を**ネイティブに使う標準的な方法がない**。
- したがって **コンテナ内のプロセス（Ollama 含む）は GPU にアクセスできず、CPU のみ**で動作する。

### 3.2 なぜ「終わらない」のか

- 使用していた **qwen2.5 7B** は、推論時に大量の行列演算を行う。
- こうした処理は **GPU 向け**であり、Apple Silicon の GPU なら数十秒程度で返せるケースが多い。
- 一方、**CPU だけ**だとコア数・メモリ帯域・演算最適化の面で不利で、**同じ処理が何十倍〜何百倍も遅くなる**。
- その結果、**1 回の生成に 5 分以上かかり、Ollama の内部タイムアウトに達してエラー** → フロントは延々と待ちぼうけ、という流れになる。

### 3.3 図で整理

```
【Docker で Ollama を動かした場合】
  Mac (Apple Silicon)
  ├── macOS … Metal / GPU ドライバ（ここに GPU がある）
  └── Docker → Linux VM
        └── コンテナ (Ollama)
              └── CPU のみ使用（GPU は VM から見えない）
              → 7B モデルが CPU のみで実行 → 極端に遅い

【Mac に直接 Ollama を入れた場合】
  Mac (Apple Silicon)
  └── macOS
        ├── Metal / GPU ドライバ
        └── Ollama（ネイティブ）
              └── GPU を直接使用 → 速い
```

**一言でいうと**  
「Docker for Mac のコンテナは Linux 環境であり、Mac の GPU をネイティブに使う経路が仕様としてないため、Ollama は CPU のみで動き、重い 7B モデルでは現実的な時間で終わらず、Ollama の 5 分タイムアウトで落ちる」という状態だった。

---

## 4. このプロジェクトでの対応（こうなってた → こう変えた）

### 4.1 以前の構成

- **docker-compose.yml** に **Ollama 用のサービス**を定義し、Next.js コンテナからは `http://ollama:11434/v1` で Ollama に接続していた。
- モデルは **qwen2.5（7B）**。
- Mac で `docker compose up` すると、Ollama も **コンテナ内（Linux VM 内）** で動作するため、**GPU は使われず CPU のみ**。
- その結果、生成に異常に時間がかかり、**Ollama の 5 分タイムアウトでエラー**。ブラウザは完了しないまま待ち続ける状態だった。

### 4.2 変更後の構成

- **Ollama を docker-compose から削除**し、**Mac 本体（ホスト OS）に直接インストール**する形に変更。
  - 例: `brew install ollama` → `brew services start ollama`
- **docker-compose.yml** には **db / mailpit / next** のみ残し、Ollama サービスは含めない。
- Next.js はこれまで通りコンテナで動かす場合、Ollama は **ホスト** で動くため、接続先を **`http://host.docker.internal:11434/v1`** に変更。
- **LLM_MODEL** は従来どおり `qwen2.5` のまま。
- これにより、Ollama は **macOS ネイティブ** として動作し、**Apple Silicon の GPU が使える**ため、生成が現実的な時間で完了するようになった。

### 4.3 ドキュメントの更新

- **root/doc/infrastructure/ollama.md** に、  
  「以前は docker-compose に組み込んでいたが、Mac の Docker 上では GPU が使えず遅延・タイムアウトするため、**Mac ではホストに直接インストールして動かす**」旨を明記。
- インストール手順（brew）、モデルの pull（例: `ollama pull qwen2.5`）、  
  および Next から見た接続設定（コンテナ時は `host.docker.internal:11434`、ローカル dev 時は `localhost:11434`）を同じ doc にまとめている。

### 4.4 補足（アプリ側の設定例）

- **app/next/.env.example** では、  
  `LLM_BASE_URL` の例として  
  - コンテナから: `http://host.docker.internal:11434/v1`  
  - ローカルから: `http://localhost:11434/v1`  
  を記載。
- LangChain の OpenAI 互換クライアント用に `OPENAI_API_KEY`（例: `ollama` やダミー値）を設定する運用のまま。

---

## 5. ほかの選択肢（A / B / C）

根本原因を踏まえると、次のような選択肢がある。

| 案 | 内容 | メリット・注意 |
|----|------|----------------|
| **A** | Docker のまま、**軽いモデル（例: qwen2.5:1.5b）** に変更 | 設定変更のみで済む。品質・表現力は 7B より落ちる可能性。 |
| **B** | **Mac に直接 Ollama をインストール**（今回採用） | GPU が使え、7B でも速く動く。docker-compose からは Ollama を外すだけ。 |
| **C** | **OpenAI API（例: gpt-4o-mini）** を使う | 環境に依存せず安定。コスト・ネットワーク・データの扱いの検討が必要。 |

本プロジェクトでは **B** を採用し、ドキュメントと compose を上記のとおり更新した。

---

## 6. まとめ

- **Mac で Docker 上の Ollama を使うと、GPU が使えず CPU のみで動く**ため、7B クラスのモデルでは生成が非常に遅くなり、Ollama の内部タイムアウト（例: 5 分）で落ちることがある。
- 「生成が終わらない」のは、タイムアウト設定の不足だけでなく、**Docker for Mac の仕様で GPU が使えないこと**が根本原因になり得る。
- **Mac で Ollama を速く使いたい場合は、Docker ではなくホストに直接インストール（例: `brew install ollama`）し、アプリからは `host.docker.internal` でホストの Ollama に繋ぐ構成**を推奨する。
